# Introduction

We propose to expose files and directories as agents.  The channels over which a process communicates with a file/dir agent can be thought of roughly as an object reference.  We propose a few means to acquire such channels.

## Use cases

Here are various scenarios under which rholang code is executing and corresponding appropriate ways of granting access to file/dir agents.

1. Launch an interpreter with an empty RSpace to process a .rho file with no user input, then exit.

   Here, lines in a config file or enumerated paths on the command line seems like the right thing to do.  There's nothing in the RSpace to begin with, and the processes in the .rho file get access to those files & directories.  When processing is complete, the interpreter exits.

2. Launch an interpreter with an empty RSpace to process a .rho file with user input (stdin or GUI), then exit.

   Here, a .rho file may be some kind of interactive thing.  So in addition to the static allocation of resources, a process should be able to request a file or dir, which causes a system file picker dialog to appear.  The user then selects a file or dir.  When processing is complete, the interpreter exits.

3. Launch a REPL with an empty RSpace.

   This is effectively the same as #2, except that the code is typed in during an interactive session rather than provided as a file.
   
4. Launch a rholang server (not on chain, just running deployments to completion) or an interpreter/REPL with a nonempty RSpace.

   Processes are long-lived. Either the server handles deployments or a "deployment" is just a new session with the nonempty RSpace.  The owner of the server should be able to put resource limits on the server and clients of the server should be able to maintain access to files between deployments.  

   There should be an allocation of ocaps to the initial deployment ("power box") process.  Future deployments don't have ambient access. The power box then governs the delegation and attenuation of these initial ocaps to clients in the form of channels to talk to file and directory agents.  If a client wants to maintain access to a file over multiple deployments, they store the channels in processes that check the client's `deployerId` in order to limit access to those ocaps in future deployments.  Unclear what happens if a file gets deleted or moved between deployments—maybe the agent just returns an error when invoking the file methods?

5. Launch an RNode where the file system is an oracle.

   a. In the weakest case, the RNode is allowed to change the files on the file system off-chain.  This case is the same as 4, but the RNode doing the deployment uses its local filesystem and the other nodes just check the processing of the data, not the accuracy of the data.

   b. Other nodes don't see the data on disk, but the shard is guaranteed that all file access is through the agent, so they can check the consistency of the oracle.  This is the same as 4 with respect to the delegation and attenuatio of ocaps.

6. Launch an RNode where the file system can be kept in sync
   Same as 4 (genesis sets up the power box), but every node in the shard has the same files.  They can check each others' file operations.

So it looks like we want four ways to grant access to the filesystem: config file for making files and directories ambiently available, command-line flag for making files and directories ambiently available, standard I/O support, and system file pickers (whether GUI dialog or command-line prompt) for dynamic access.  Processes get three different APIs: one for getting the file/dir agents from the registry (config file & flag), one for using std{in,out,err}, and a third for triggering a file selection prompt (file picker).

Oracular access suffices for all scenarios except the last above.  Since there are extra problems to solve when keeping a file system in sync across nodes in a shard—for example, how a process can regain access to a file if a node in a shard goes down, how a node should react to corrupted data or other hardware failures, etc.—we defer those to another proposal.

# Statically provisioning files and directories

One can statically provision file/dir access in one of two ways: with a config file entry or with flags.  This approach provides permanent, ambient access to the files or directories until the node is restarted.

## With the config file

Keys name files made statically available through the `fs.openFile` and `fs.openDir` methods.  Values are either string paths (defaulting to full access) or a record with options. For files:

| Mode string | Description |
|-------------|-------------|
| `"r"`       | Open an existing file for reading. Fails if the file does not exist. |
| `"w"`       | Open a file for writing. Creates it if needed; truncates it to empty if it already exists. |
| `"a"`       | Open a file for appending. Creates it if needed; writes go to the end of the file. |
| `"r+"`      | Open an existing file for both reading and writing. Fails if the file does not exist. |
| `"w+"`      | Open for reading and writing. Creates if needed; truncates existing file. |
| `"a+"`      | Open for reading and appending. Creates if needed; writes go to the end. |
| `"wx"`      | Create a new file for writing; fail if it already exists. |
| `"w+x"`     | Create a new file for reading and writing; fail if it already exists. |

If the mode is left unspecified, it defaults to "r".

```
storage {
  oracle-static-files = {
    "relative/path": { "path": "/absolute/path/to/file", "mode": "r+" },
    "some/other/relative/path": "/abs/path/to/dir",
  },
  consensus-static-files = {
    "relative/path": "/absolute/path/to/file2",
    "some/other/relative/path": "/abs/path/to/dir2",
  }
}
```

Here and below in path parameters, paths used by Rholang code must be UTF-8 strings.  Directories must be trees: no symbolic or hard links (though we might later enable them with a flag).  The node should fail to launch if either of these are not true.

## With flags

One can repeat the flag for each file or directory.

```
--oracle-static-file '"relative/path"={"path":"/absolute/path/to/file","mode":"r+"}' \
--oracle-static-dir '"some/other/relative/path"="/abs/path/to/dir"' \
--consensus-static-file '"relative/path"="/absolute/path/to/file"' \
--consensus-static-dir '"some/other/relative/path"="/abs/path/to/dir"'
```

## Standard I/O

Standard input, output, and error are exposed as three methods on the `fs` agent that each return a file-agent instance wired to the underlying native handle.  There is no separate URN for stdio; bumping `rho:io:fs:1.*` is enough if the shape ever changes.

The `fs` agent privately defines (at least) two additional file-agent classes alongside the regular `File` class:

* `ReadOnlyStream` — backs `stdin`.  Supports `text`, `lines`, `forEachLine`, `mapReduceLines`, `mapReduceLinesOrdered`, plus a forward-only `readLine()` and `read(n)` (consume `n` bytes, advancing the cursor).  Positional methods (`readAt`, `seek`, `tell`, `size`, `truncate`, `writeAt`) are *not* on a stream: calling them lands in the class's `default` and returns `[false, FSERR_UNSUPPORTED, ...]`.  Maintaining a growing buffer of every byte ever read so positional access could work retroactively would be unbounded memory for no real-world gain; clients who want positional access can redirect stdin to a file and open that file through `fs`.
* `AppendOnlyStream` — backs `stdout` and `stderr`.  Supports `appendLines`, `write(bytes)`, and `flush()`.  Read methods land in `default` and return `[false, FSERR_UNSUPPORTED, ...]`.

Usage:

```
new getFS(`rho:io:fs:1.*`), notify in {
  for (fs <- getFS!?(*notify)) {
    try @stdin  <- fs!stdin()  {
      try @lines <- stdin!lines() {
        // use lines
      }
      catch @[code, msg] {
        // handle lines error
      }
    }
    catch @[code, msg] {
      // handle stdin error
    } ; // wait for input before providing output

    try @stdout <- fs!stdout() {
      try <- stdout!appendLines(["hello", "world"]) {
        // continue
      }
      catch @[code, msg] {
        // handlde appendLines error
      }
    }
    catch @[code, msg] {
      // handle stdout error
    }
  }
}
```

Per-use-case availability (referencing §Use cases 1–6):

* Case 1 (batch `.rho`, no input): `fs!stdin()` succeeds, but the returned instance yields EOF on the first read.  `stdout`/`stderr` go to the process's actual stdio.
* Cases 2 & 3 (interactive `.rho` / REPL): all three are wired to the terminal.
* Cases 4–6 (server / RNode): all three default to `/dev/null`-equivalent instances; the power box can override at genesis (e.g., to wire stdio to gRPC streams for a network-hosted REPL).

On a multi-node shard the lead node's stdin reads are captured and replayed to followers as non-deterministic events, the same machinery used for `rho:io:grpcTell`.

The existing flat `rho:io:stdout` and `rho:io:stderr` URNs remain available for legacy code.  They behave like `fs!stdout()` followed by `stdout!write(...)` with no error tuple, intended for one-shot debug printing.

# Acquiring agent references

If a process already has an agent for a directory, it can open files in the directory with the `open` method below.  But to get a file or directory agent to begin with, it has to use either the statically declared ones or a file picker.

## Errors

In an async message-passing platform like Rholang, it's conceivable that one could register a process for handling errors so the happy path isn't interrupted by error handling:

```
new errorHandler in {
  contract errorHandler(@file, @line, @errorCode, @errorMsg) = {
    // handle errors
  } |
  file!onError(*errorHandler);
  // process the file
  P
}
```

But that tends to separate the error handling from the place where the error occurs, making it harder to reason locally about code.  This proposal recommends returning a list from each method, either `[true, result]` or `[false, error code, error message]`.  Clients will typically invoke methods using pattern matching:

```
for (@[ok, ...rest] <- file!method(...args)) {
  if (!ok) {
    let @[code, msg] <- rest in {
      // handle error
    }
  } else {
    let @[result] <- rest in {
      // handle result
    }
  }
}
```

The particular codes and messages will be specific to the implementation of the File API.

### Error syntax

The big `if` block and destructuring assignment in each case is a lot of boilerplate.  Instead we propose a try/catch syntax:

```
⟦
try @result <- file!method(...args) {
  // handle result
}
catch @[code, msg] {
  // handle error
}
⟧ =
for (@[ok, ...rest] <- file!method(...args)) {
  if (ok) {
    let @[result] <- rest in {
      // handle result
    }
  } else {
    let @[code, msg] <- rest in {
      // handle error
    }
  }
}
```

The try-line pattern (`@result`) is optional; methods that return `[true]` alone (e.g. `close`, `flush`, `rename`) are written `try <- ...`, in which case the success branch drops the `let` and runs the try body directly.

#### No `finally` clause

An earlier draft of this FIP included a `finally { ... }` block that would run after either the try or catch body completed.  This is not implementable as sugar: Rholang branch bodies can be asynchronous (a body that ends by starting a `for`-receive doesn't complete when the textual `{ ... }` ends), so a keyword-based finally would silently race the branch it's supposed to follow.

Two idioms cover the common needs:

**"Run in parallel with the try/catch."**  Just use `|`.

```
try @result <- file!method(...args) {
  // handle result
} catch @[code, msg] {
  // handle error
} |
// runs concurrently with whichever branch fires
R
```

**"Run after either branch signals it's done."**  Have each branch send on a shared `done` channel and receive from it in parallel:

```
new done in {
  try @result <- file!method(...args) {
    P; done!()
  } catch @[code, msg] {
    Q; done!()
  } |
  for (<- done) {
    // code to run once either P or Q has signaled completion
    R
  }
}
```

This puts the "when am I done" decision in the branch author's hands, where it belongs — the sugar has no way to determine it automatically.

## The `openFile` and `openDir` methods of `io:fs`

The `openFile` method takes a path and an optional options map.  Its `mode` field accepts any of the file mode strings from the static-configuration table above (`"r"`, `"w"`, `"a"`, `"r+"`, `"w+"`, `"a+"`, `"wx"`, `"w+x"`); the default is `"r"`.

The `openDir` method takes a path and an optional options map.  Its `mode` field accepts only two strings, matching the two ways a directory capability can be exercised on a POSIX filesystem:

| Mode string | Description |
|-------------|-------------|
| `"r"`       | The directory agent permits the read-side methods only: `entries`, `exists`, `stat`, and `openFile` (which itself is restricted to file mode `"r"`).  This is the default. |
| `"rw"`      | The directory agent additionally permits `openFile` with any file mode, plus `removeFile`, `removeDir`, `rename`, `copyFile`, `chmod`, `chown`, and `openDir` with `path: true`. |

The static-configuration table at the top of this document defines the file mode strings.  Static directory entries use the directory mode strings above; if no `mode` field is given, the directory entry defaults to `"rw"` for `--*-static-dir` flags and to `"r"` for `*-static-files` config blocks (the same default-permissive-vs-default-restrictive distinction the FIP already draws for the flag and config-file forms).

The options map on `openFile` and `openDir` also accepts:

* `"create": Bool` (`openFile` only) — only meaningful in combination with mode `"r+"` (the other write-capable file modes already imply creation).  When `true`, `openFile` opens the file for read+write, creating it if it does not exist and *not* truncating it if it does, equivalent to POSIX `open(O_RDWR | O_CREAT)`.  This combination is not in the fopen-style mode table because fopen itself does not name it; the option fills that gap.
* `"path": Bool` (`openDir` only) — `mkdir -p`-style ancestor creation.  Requires the parent dir agent to have been opened with `mode: "rw"`.

Assuming the config file entry or flags above:

```
new getFS(`rho:io:fs:1.*`), notify in {
  for (fs <- getFS!?(*notify)) {
    try @[dir] <- fs!openDir("some/other/relative/path") {
      try @[file] <- fs!openFile("relative/path")) {
        // invoke file & dir methods
      }
      catch @[code, msg] {
        // handle openFile error
      }
    }
    catch @[code, msg] {
      // handle openDir error
    }
  }
}
```

# API

## File Agent methods

The examples below assume a file agent named `file`.

### Per Line

File agents provide line-based access to text files, allowing reading from the beginning and appending to the end.  File agents maintain a mutex to prevent extending a file while it's being read and vice versa.  They also maintain a mutex to prevent positional access (see below) while using line-based methods and vice versa.

##### `text` method

The `text` method returns the contents of the file as a single string.

```
try @text <- file!text() {
  // handle text
}
catch @[code, msg] {
  // handle error
}
```

##### `lines` method

The `lines` method reads the entire file, splits the string using the regular expression `\R` (Unicode line break), and returns the resulting list of strings.
```
try @lines <- file!lines() {
  // handle lines
}
catch @[code, msg] {
  // handle error
}
```

We should deprecate this once we have regular expressions.

##### `mapReduceLines` method

The `mapReduceLines` method processes lines of a text file in parallel, accumulating the results.  It streams the file; as it encounters Unicode line breaks, it invokes a contract to accumulate the line.  It then combines the results using the provided function and returns the fully accumulated value.

```
new reduce in {
  contract reduce(accumulatorCh, @line) = {
    // Acquire accumulator
    for (@accumulator <- accumulatorCh) {
      // combine accumulator with the line
      accumulatorCh!(newAccumulator)
    }
  } |
  try @result <- file!mapReduceLines(init, reduce) {
    // do something with the
    // fully accumulated value
  }
  catch @[code, msg] {
    // handle error
  }
}
```

##### `mapReduceLinesOrdered` method

The `mapReduceLinesOrdered` method behaves the same as `mapReduceLines` but guarantees to accumulate the lines in order.

```
new reduce in {
  contract reduce(ret, @accumulator, @line) = {
    // combine accumulator with the line
    ret!(newAccumulator)
  } |
  for @result <- file!mapReduceLinesOrdered(init, reduce)) {
    // do something with the
    // fully accumulated value
  }
  catch @[code, msg] {
    // handle error
  }
}
```

##### `appendLines` method

The `appendLines` method takes a list of strings and appends them to the end of the text file.

```
try <- file!appendLines(lines) {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
```

### Positional

File agents provide positional access to files.  Positional access relies on acquiring read and write locks for regions of the file, allowing multiple readers and single writers of overlapping regions.  Data in a region cannot be read while a writer has a lock on it.  Also, file agents maintain a mutex to prevent simultaneous line-based access and positional access.

#### Bytes

Byte-level methods take and return `ByteArray` values, matching the existing cryptographic system processes.

| Method | Signature | Notes |
|--------|-----------|-------|
| `read` | `(n) -> bytes` | Reads up to `n` bytes from the current position and advances it.  At EOF the result tuple's payload is an empty `ByteArray`. |
| `readAt` | `(offset, n) -> bytes` | Positional read; does not move the current position. |
| `write` | `(bytes) -> nWritten` | Writes at the current position and advances it. |
| `writeAt` | `(offset, bytes) -> nWritten` | Positional write; does not move the current position. |
| `seek` | `(offset, whence) -> newPos` | `whence ∈ {"set","cur","end"}`. |
| `tell` | `() -> pos` | Current position. |
| `size` | `() -> nBytes` | Current file size. |
| `truncate` | `(n)` | Sets the file size to `n`, padding with zeros if the file grows. |
| `flush` | `()` | Forces a durable write. |
| `close` | `()` | Releases the handle; subsequent calls return `FSERR_CLOSED`. |

**Range locking.**  The byte-level surface uses range locks: multiple readers, single writer of overlapping byte ranges.  Two ways to use them:

* *Implicit (default)*: each byte-level method auto-acquires the right kind of lock over the byte range it touches, for the duration of the call.  Conflict returns `[false, FSERR_BUSY, ...]`.  An options map argument `{"wait": true}` blocks until the lock is acquired instead of failing.
* *Explicit*: `lockRange(offset, length, mode) -> lockToken` and `lockToken!release()`.  Held locks compose with implicit locks across calls.  `mode ∈ {"r","w"}`.  The lock token is itself a small agent, returned as `bundle+`, so callers can hand it to others without granting `release` by interposing a forwarder.

The line-vs-byte mutex described in the §"Per Line" intro is independent of and orthogonal to range locking: attempting any byte-level method while a line-based call is in flight (or vice versa) returns `FSERR_BUSY` regardless of byte range.

### Listing and metadata

##### `entries` method

Returns the immediate children of the directory as a list of entry records.  Each record has the shape:

```
{
  "name":  String,         // basename only; never contains "/"
  "kind":  "file" | "dir" | "other",
  "size":  Int,            // bytes for files; omitted for non-files
  "mode":  String,         // 9-character symbolic permission string, e.g. "rwxr-xr-x"
  "mtime": Int,            // seconds since the Unix epoch
  "ctime": Int,            // seconds since the Unix epoch
  "atime": Int,            // seconds since the Unix epoch
  "owner": String,         // username
  "group": String          // group name
}
```

The `mode` field is a 9-character string of three rwx triples — owner, group, other — exactly the form `ls -l` displays after the file-type character.  Each triple is three positional characters in order `r`, `w`, `x`; an unset bit is written as `-`.  For example, `"rwxr-xr-x"` is owner rwx, group rx, other rx, and `"rw-r--r--"` is owner rw, group r, other r.  This matches the form `chmod` below accepts.  Setuid/setgid/sticky bits and ACL extensions are not exposed.  Inode numbers are also not exposed — they are host-specific and have no use to Rholang code.

(Symbolic links are excluded by FIP-level requirement: a directory must be a tree, as stated under "With the config file" above.  `kind` therefore never reports `"symlink"`.)

The list is sorted lexicographically by `name` in UTF-8 byte order, so the result is deterministic across nodes regardless of host directory-iteration order.

```
try @result <- dir!entries() {
  // handle entries
}
catch @[code, msg] {
  // handle error
}
``` 

##### `exists` method

Returns `true` if a relative path exists under the directory root.

```
try @exists <- dir!exists("notes/todo.txt")) {
  if (exists) {
    // do something
  } else {
    // do something else
  }
}
catch @[code, msg] {
  // handle error
}
``` 

##### `stat` method

Returns an entry record (the same shape as `entries` above) for a relative path.

```
try @entry <- dir!stat("notes/todo.txt")) {
  // handle entry
}
catch @[code, msg] {
  // handle error
}
```

### Creating scoped agents

##### `openFile` method

Creates a file agent (or returns a cached one) and returns that agent channel. If the options map has the `create` field set to `true` and the file does not already exist, it creates the file itself on the file system.

```
try @file <- dir!openFile("notes/todo.txt", {"create": true}) {
  // use file
}
catch @[code, msg] {
  // handle error
}
```

##### `openDir` method

Creates a directory agent (or returns a cached one) scoped to the given relative subdirectory and returns that agent channel.  If the options map has the `path` field set to `true`, it will create all the ancestor subdirectories if they don't exist.  `path: true` requires the parent directory agent to have been opened with `"mode": "rw"`.

```
try @notesSubDir <- dir!openDir("notes", {"path": true}) {
  // use notesSubDir
}
catch @[code, msg] {
  // handle error
}
``` 

### File and directory management

All mutating operations must be atomic when the underlying filesystem supports it (notably `rename`), and otherwise must fail cleanly.

##### `removeFile` method

Deletes a file.

```
try <- dir!removeFile("notes/old.txt") {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
``` 

##### `removeDir` method

Takes a path and (optionally) an options map. Deletes a directory.  
If the `recursive` entry of the options map is `true`, it deletes its contents first.

```
try <- dir!removeDir("notes/archive", {"recursive": true}) {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
``` 

##### `rename` method

Renames (moves) a path under the same directory root. Implementations should prefer an atomic rename.  If the rename would cross filesystems and therefore cannot be atomic, the method returns `[false, FSERR_CROSS_DEVICE, ...]` rather than silently degrading to copy + delete; callers who want copy semantics can use `copyFile` followed by `removeFile`.

```
try <- dir!rename("notes/todo.txt", "notes/todo.done.txt") {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
```

##### `copyFile` method

Copies a file from one relative path to another.

```
try <- dir!copyFile("notes/todo.txt", "notes/todo.bak") {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
```

### Permission management

##### `chmod` method

Changes the POSIX permission bits of a file or directory.  The mode argument is a 9-character string of three rwx triples — owner, group, other — exactly the form `entries` and `stat` report in the `mode` field.  Each triple is three positional characters in order `r`, `w`, `x`; an unset bit is written as `-`.  For example, `"rw-r--r--"` is owner rw, group r, other r; `"rwxr-xr-x"` is owner rwx, group rx, other rx.  Any other 9-character pattern (a non-`-` character outside the rwx position, or fewer/more than 9 characters total) is rejected with `FSERR_BAD_ARG`, as are symbolic-delta forms like `"u+x"`.  Setuid/setgid/sticky bits cannot be set this way.

On a file agent (operates on the file the agent represents):

```
try <- file!chmod("rw-r--r--") {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
```

On a directory agent (takes a relative path):

```
try <- dir!chmod("notes/todo.txt", "rw-r--r--") {
  // response is empty, so continue
}
catch @[code, msg] {
  // handle error
}
```

`chmod` requires the relevant agent to have been opened in a write-capable mode (any of `"r+"`, `"w"`, `"a"`, `"w+"`, `"a+"`, `"wx"`, `"w+x"` for files; `"rw"` for directories).

##### `chown` method

Changes the owner and/or group of a file or directory.  Both arguments are strings resolved against the host user/group database; passing the empty string `""` for either means "do not change."  Numeric uid/gid values are not exposed at the Rholang surface — they are host-specific and non-portable.

```
try <- file!chown("alice", "staff") { ... } catch @[code, msg] { ... }
try <- dir!chown("notes/todo.txt", "alice", "") { ... } catch @[code, msg] { ... }
```

On a multi-node shard `chown` executes on the lead node — `/etc/passwd` and the rest of NSS are consulted on that node only — and is recorded as a non-deterministic event for replay on the others.  Like `chmod`, `chown` requires the relevant agent to have been opened in a write-capable mode.

## Useful Ocaps patterns

### Attenuation

Here's an example of creating a filtering forwarder that filters out methods that write to a file while forwarding the rest.

```
contract makeReadOnly(ret, @file) = {
  new ro in {
    contract ro(@[r, method, args...]) = {
      match method {
        "appendLines" => @r!([false, FSERR_UNSUPPORTED, "Unsupported"])
        "write" => @r!([false, FSERR_UNSUPPORTED, "Unsupported"])
        "writeAt" => @r!([false, FSERR_UNSUPPORTED, "Unsupported"])
        "truncate" => @r!([false, FSERR_UNSUPPORTED, "Unsupported"])
        _ => file!(@r, method, args...)
      }
    }
  } |
  ret!(bundle+{*ro})
} |
for (roFile <- makeReadOnly!?(file)) {
  // roFile behaves like file but has no write methods
  try @lines <- roFile!lines() {
    // handle lines
  }
  catch @[code, msg] {
    // handle error
  }
}
```

Similar code can validate inputs or censor outputs.

### Membranes

A membrane forwards method calls to an underlying agent, but wraps the result of the call in an object that performs some security purpose.  For example, suppose you have a directory object that you want to lend for a fixed time; with a membrane, you can

1. revoke access to the directory agent and to all the file agents obtained through the directory agent by sending a single message
2. log all access to files
3. limit the amount of time that the filesystem can block

## Standard error codes

Every method described above returns its error tuple using one of the following codes.  Implementations are free to add more, but should not reuse these meanings.

| Code | Meaning |
|------|---------|
| `FSERR_UNSUPPORTED` | Method disallowed by attenuation or by the underlying class (e.g., `appendLines` on `ReadOnlyStream`, `seek` on `stdin`). |
| `FSERR_NOT_FOUND` | The named path does not exist. |
| `FSERR_EXISTS` | The named path exists and the requested mode (`"wx"`/`"w+x"`) forbade overwrite. |
| `FSERR_PERM` | The host operating system denied permission. |
| `FSERR_IO` | An underlying I/O failure. |
| `FSERR_BUSY` | A range lock or the line-vs-byte mutex prevented the operation. |
| `FSERR_REVOKED` | A membrane around this capability has been revoked. |
| `FSERR_QUOTA_EXCEEDED` | The associated quota agent declined to charge the requested resource. |
| `FSERR_CLOSED` | Operation attempted on a closed handle. |
| `FSERR_QUARANTINE` | The path canonicalizes outside the directory root or traverses a symlink. |
| `FSERR_CROSS_DEVICE` | A `rename` would have to cross filesystems and cannot be atomic. |
| `FSERR_BAD_ARG` | A mode string, offset, owner/group name, or other argument was malformed or unknown. |
