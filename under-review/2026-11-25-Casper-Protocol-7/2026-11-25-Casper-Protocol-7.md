# Casper Protocol 7

AUTHOR_LINE  
2026-11-25

## Summary

This proposal asks for approval to activate Casper protocol 7, the cost-accounted protocol, on a production shard. The F1R3FLY.io maintainers ratified the protocol number and its activation rule on 2026-09-16 in decision D-01. That rule requires this FIP: protocol 7 activates only through a fresh genesis after FIP approval.

The implementation is in [f1r3node-rust PR #1118][pr1118], which targets the `ca-canary` release branch. That pull request makes protocol 7 the default for a new genesis on development and test shards. It does not activate protocol 7 on a production shard.

## Motivation

Protocol 1, the protocol before cost accounting, makes every validator execute every deploy before it proposes. A validator that falls behind on execution stops proposing, and the shard can stall. Protocol 7 separates ordering from execution. Validators agree on an order of unexecuted deploys first, and every node then executes the finalized order. Deploy cost is accounted from that execution.

## Specification

### Protocol 7 content

The version table in the Consensus Protocol document defines protocol 7 as follows:

- **Order then execute.** A proposer puts unexecuted deploy envelopes into a block. Validation is structural and replays no deploy. When the last finalized block advances, every node executes the finalized blocks in one canonical order and records the result of each block. The tranche 1 plan describes the executor.
- **Shard resource policy.** A block has a demand cap. With the default policy, the cap is 5,845,811 phlo. A deploy cannot declare a phlo limit above the cap. The phlo cap of a protocol 7 node is the smaller of `max-phlo-limit` and the demand cap (`resource_policy.rs`).
- **Exact accounting effect identity** (D-04). A failed deploy body with verified settlement contributes an applied accounting effect.
- **Additive merge composition** (D-08). Merges use additive multiset composition, with causal rejection closure and locally verified merge evidence.
- **Domain-separated deploy lookup identity** (D-10). The repeat-deploy carrier index looks up deploys by a domain-separated identity.

### Version authority

Decision D-01 makes these rules normative. The rules name protocol 6, the number on the cost-accounting branch when the maintainers compared it. D-01 replaces that number with 7.

- The genesis ceremony master writes the configured protocol version into the genesis candidate. Each approver compares it with its own configured version before it signs.
- Approved-block validation rejects every version outside the supported set of the node binary.
- Every node adopts the approved version into its running shard configuration.
- Every proposal carries the running version. No compile-time default bypasses it.
- Peer filtering and block validation compare against the running version and no other source.

### Accounting authority version 8

The accounting authority version is 8. It versions the node accounting module, not the Casper protocol, and the two numbers change independently. The node status API reports both numbers as `casperProtocolVersion` and `accountingAuthorityVersion` (API reference).

## Activation

- Protocol 7 activates only through a fresh genesis. No node-local switch, A/B mode, or block-height window exists.
- A shard that started with protocol 1 keeps protocol 1. An operator moves to protocol 7 by starting a new shard, so every running shard needs a new genesis to use protocol 7.
- After this FIP is approved, the protocol 7 row of the version table gets a link to this FIP and the activation date. Today the row records only the ratification date.

### Conditions from the ratified decisions

The decisions add these conditions to the activation. This FIP is the approval that each of them names.

| Decision | Condition | Status |
| --- | --- | --- |
| D-01 | FIP approval and a fresh genesis | Open. This FIP |
| D-08 | FIP approval, a fresh genesis, differential tests, a compatibility analysis, and accounting-conservation evidence | Open |
| D-10 | The protocol 7 FIP fixes the exact envelope commitment of the deploy lookup identity. `CLAIM-FINALITY-002` stays pending until its differential and soak gates pass | Open |

## Open questions

1. Which differential tests, compatibility analysis, and accounting-conservation evidence satisfy D-08?
2. What is the exact envelope commitment of the protocol 7 deploy lookup identity (D-10)?
3. Does the read-only observer role need its own version adoption rules, or does it inherit them from approved-block validation? D-01 leaves this question open.
4. When does the first production shard start with protocol 7?
