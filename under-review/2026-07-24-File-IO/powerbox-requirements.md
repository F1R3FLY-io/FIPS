# Powerbox — requirements & tracking

**Status:** design-in-progress; no code shipped. Consolidates all
powerbox-related requirements from the File I/O FIP spec and all
powerbox-related deferrals accumulated during Phase 6 slices 16-19.

Not itself a phase. When the powerbox slice lands, this document is
the acceptance-criteria checklist.

## 1. Purpose

The powerbox is the runtime component that hands each authenticated
principal (deployer) a **distinct, attenuated `Fs` capability** at
deploy time. Without it, the File I/O FIP's ocap discipline collapses
to a shared-Fs model where any deploy can affect any other.

Two things the powerbox is NOT:
- It is not a Rholang library (it lives in the Rust runtime, injecting
  per-deploy bindings before user code executes).
- It is not the static-provisioning config loader (Phase 7 produces
  the config; the powerbox consumes it).

## 2. Spec requirements

| # | Spec § | Requirement |
|---|--------|-------------|
| R-1 | §842-844 | `Fs.stdin()` / `stdout()` / `stderr()` return caps wrapping fds the powerbox supplies at Fs mint time. |
| R-2 | §865-867 | The Fs-cache does not cross Fs boundaries. Each principal receives its own Fs instance from the powerbox; those instances do not share state. |
| R-3 | §867 | The powerbox delivers the Fs cap via a `bundle+` on the powerbox's per-grantee `new` scope; caller code cannot fabricate another principal's Fs. |
| R-4 | §869 | Subordinates receive attenuated caps (File, Dir, membrane-wrapped), NOT `Fs`. Any subordinate who receives an `Fs` receives it directly from the powerbox with its own per-principal static bundle. |
| R-5 | §826, §874, §889 | Deploys obtain `Fs` via `getFS(`rho:io:fs:1.*`)` — a Versioned Registry lookup.  ~~The powerbox is the URN resolver for `rho:io:fs:1.*` and returns a per-principal cap.~~  **Revised 2026-07-30:** `rho:io:fs:1.*` is a static URN literal resolved at deploy-time normalization via the versioned registry (`insertVersion` alias installed by fs_generator, PB-B-3). Dynamic URN construction / runtime URN lookup is out of scope for the File I/O FIP. |
| R-6 | §Storage cases 4-6 | ~~Powerbox default for stdio in non-oracle deploys is `/dev/null`-equivalent (empty stdin, discard stdout/stderr); powerbox may override per-principal per config.~~  **Revised 2026-07-30 (PB-M-1 resolution):** with a shared `Fs` cap, stdio is a node-process-wide setting — the fds `Fs` is minted with (currently (0, 1, 2) at genesis) apply to all deploys.  Operators who want to redirect stdout/stderr to a file or `/dev/null` do so via routine node config (`--stdio-stdout <path>` etc., if such flags are added).  Not a per-principal concern; not a powerbox concern. |
| R-7 | §425, §802 | The buffer allocator is published to the versioned registry at `rho:lang:buffer:1.0.0`. Per the implementation plan §37 and §494 the allocator is handed out per-principal by the powerbox — same treatment as `Fs`. |

Rejected model 2 (powerbox pre-approves at cap handout via attenuated caps) — less flexible, doesn't handle mid-deploy quota changes. |
| R-9 | §1416 | ~~On `"FSERR_REVOKED"` a subordinate re-requests a fresh capability from the powerbox. The powerbox's policy (deployerId match, time window, etc.) decides grant vs refuse. Requires a per-principal `getFs`-style re-request surface.~~  **Revised 2026-07-30 (PB-M-10 resolution):** `FSERR_REVOKED` is a pure user-space ocap concern.  Membranes (spec §1392) let Alice hand Bob revocable access to a File cap that Alice already holds.  Bob's "recovery" after seeing `FSERR_REVOKED` is: call `getFs` and try `openFile(name)` normally — success iff the current config lists `name`; failure iff not.  The powerbox has no policy engine to consult about the revocation event itself.  Membranes are useful precisely because config-listed access is public: they let Alice share access to a path that the config used to list but no longer does, or to attenuate an access mode. | R-10 | §23 (Rationale §Ocap) | "Authority to touch the host filesystem comes only from statically-provisioned caps at genesis, delegated through the powerbox. There is no ambient 'just open any path.'" A user deploy binding raw `rho:io:fs:native:*` URNs violates this outright. |
| R-11 | Plan §37, §494, §532 | Interim stub Powerbox mints one `Fs` (and one allocator) per authenticated `deployerId` extracted from `NormalizerEnv`'s `rho:deploy:data` + `rho:system:deployerId:ops`. URN lookup shape stays stable across the eventual real-powerbox transition — only the delegation policy changes. |
| R-12 | Plan §115 | The static-provisioning bundle (Phase 7 output) is handed to the powerbox at genesis; the powerbox uses it to construct per-principal bundles. |
| R-13 | §1258, §1288, Plan §353-368 | Config schema distinguishes `oracle-static-*` from `consensus-static-*` buckets. Under Consensus mode `chown` is `FSERR_UNSUPPORTED` and `stat`/`entries` omit host-transient fields (mtime/ctime/atime/owner/group).  ~~The powerbox routes each principal to the right bucket based on the principal's mode; principals in Consensus mode receive Fs caps whose underlying handlers enforce field-omission and chown-refusal.~~  **Revised 2026-07-30 (Q-7 resolution):** mode is per-**file/dir**, not per-principal. A single principal can hold both consensus and oracle caps concurrently.  Bucket path sets are mutually exclusive (PB-M-16). |
| R-14 | §1424, §Interactive use cases | Optional `sys:ui` cap (`filePicker` / `dirPicker`) is available on interactive use cases (2, 3) only, gated by `--enable-ui-picker`. The powerbox decides whether to hand out `sys:ui` per principal; in non-interactive contexts or with the flag off, lookup returns `FSERR_UNSUPPORTED`. Not a File I/O FIP surface but the same powerbox handout model. |
| R-15 | §826, §874, §889 wildcard form | Deploys may use `` `rho:io:fs:1.*` `` (Versioned Registry wildcard) as well as `` `rho:io:fs:1.0.0` ``.  ~~The powerbox is the resolver for both forms~~  **Revised 2026-07-30:** the versioned registry resolves both forms at deploy-time normalization; wildcard maps to the highest compatible version installed at genesis (via `insertVersion` — PB-B-3).  No powerbox / no runtime URN lookup involved — see R-5 revision for the deploy-time-only URN model. |

## 3. Open issues

Issues surface as `PB-{severity}-N` (B blocker, M major, m minor).
Grouped by originating phase.

### Phase 1 — Native filesystem primitives

| ID | Severity | Description |
|----|----------|-------------|
| **PB-B-4** | ~~Blocker~~ **Subsumed by PB-B-1 fix 2026-07-30** | `handlers.rs::fs_open` (and every other native handler) trusts the caller-supplied `root` path unconditionally.  `safe_descend` guards only the `rel` portion against escape from the supplied root — the root itself is assumed already-canonicalized and symlink-checked.  Under the R-3 model this trust is safe: only the (blessed, per-principal) `Fs` agent constructs `root` from a powerbox-provisioned bundle.  Once PB-B-1's phase-scoped URN visibility lands, user code cannot bind fs-native URNs directly, so the `Fs` agent is the only supplier of `root` — trust is restored to its intended invariant. |
| **PB-B-2** | Blocker (was Slice 19 Security B-19-2) | `handle_table.rs` uses a per-runtime `HashMap<u64, FileHandle>` shared across all tenants with monotonic fd allocation.  `fs_close` / `fs_read` / `fs_write` / `fs_truncate` accept any fd with no ownership check.  Any deploy with fs-native URN access can iterate small fds and close/read/write files opened by any other tenant.  Predates Phase 6 — the ownership check was always missing; PB-B-1's filter had been keeping user code from exercising it. |

### Phase 2 — UTF-8 helpers and `concatBytes`

No powerbox surface — three stateless native helpers (`validUtf8PrefixLen`, `decodeUtf8`, `concatBytes`) with no capability content.

### Phase 3 — Buffer library + allocator

| ID | Severity | Description |
|----|----------|-------------|
| **PB-B-5** | Blocker | The allocator (`Allocator` agent in `Buffer.rho`) is not yet wired to a registry URN and has no per-principal delegation.  Per R-7 / R-11, when it ships the powerbox must hand out a distinct allocator per authenticated `deployerId` at `rho:lang:buffer:1.0.0`.  Same shape as Fs.  Not yet a runtime hole because the allocator is unpublished; becomes a blocker as soon as it lands. |
| **PB-M-6** | Major.  **Shape resolved 2026-08-03 (model 1).** | `FSERR_QUOTA_EXCEEDED` quota-agent hook is deferred in Buffer.rho:641-651 with a TODO. | **PB-M-7** | Major | Allocator handout inside the Rholang genesis composition — like `Fs`, the `Allocator` agent is currently a module-level name in the FsGenesis new-scope (slice 19 `compose_fs_genesis_source`).  If exported to deploy scope directly it becomes a shared allocator (violates R-7).  Powerbox slice must gate `Allocator` export the same way as `Fs`. |

| ID | Severity | Description |
|----|----------|-------------|

### Phase 5 — File / Dir library

| ID | Severity | Description |
|----|----------|-------------|
| **PB-M-8** | ~~Major~~ **Subsumed by PB-B-1 fix 2026-07-30** | `File.rho` and `Dir.rho` store `canonRoot` in per-agent state as a trusted invariant (spec §Dir "canonRoot is IMMUTABLE from the initial ctor call: it is the boot-canonicalized sandbox root").  Under R-3, only the powerbox-provisioned Fs mints these agents with a canonicalized root.  Once PB-B-1's phase-scoped URN visibility lands, user code cannot reach the fs-native URNs and therefore cannot construct File / Dir agents with an attacker-controlled `canonRoot`; the invariant is restored. |
| **PB-M-9** | ~~Major~~ **Resolved 2026-08-03 (option a: allow).** | `File.readInto` / `File.writeFrom` / `File.readLineInto` etc. accept a `Buffer` cap as an argument.  Under the eventual per-principal model, a caller's Buffer and their File must be co-tenant (both minted by the same principal's allocator + Fs).  Cross-tenant buffer-to-file writes are currently possible (both are shared), and after per-principal delegation there is no runtime check preventing Alice from passing her Buffer to Bob's File.write.  **Resolution: option (a) — allow.**  Buffers are transferable caps.  Alice handing her Buffer to Bob's `File.writeFrom` is a legitimate ocap pattern (Alice grants Bob write-through-my-buffer authority; Alice can revoke via close).  No runtime check needed; no `FSERR_UNSUPPORTED` on cross-tenant.  Matches the "buffers as first-class values" ocap semantics already exercised elsewhere.  Options (b) refuse and (c) tag-at-mint rejected — both introduced a runtime discrimination for a distinction the ocap model doesn't require. |

| **PB-M-13** | Q-6 resolution 2026-07-30 (crash-recovery re-close) | On `RhoRuntimeImpl` startup, walk the tuplespace and rewrite every File agent whose state is `"open"` to `"closed"` — the fd table is per-runtime and gone across restarts. | **PB-M-14** | Q-6 resolution 2026-07-30 (consensus-mode filesystem WAL) | Every mutating operation on a `consensus-static-*` path (`write`, `writeAt`, `truncate`, `chmod`, `chown`, `remove*`, `rename`, `copy*`) is journaled to the block as a WAL entry BEFORE being applied to the underlying store.  A joining node replays the WAL against a base image (from the latest snapshot, see PB-M-15) to reconstruct current filesystem contents.  Determinism requirement: WAL entries carry only the operation kind + resolved-path + payload; host-transient fields (uid/gid on `chown`, timestamps) are omitted or normalized (identical to `stat_record`'s field-omission rule).  **Payload rule 2026-08-03 (hash-only):** WAL entries carry a **cryptographic hash** of the bytes read/written, NOT the bytes themselves — with one exception: bytes that arrived as part of a deployment (i.e., are already part of the block payload as deploy data) may be referenced directly.  This bounds the on-block WAL size to `O(hash_len × ops)` regardless of write volume; joining nodes fetch the actual byte payloads separately over the network (protocol TBD) and validate against the hashes in the WAL.  Reads that consume file bytes must record the resulting hash so replay produces a byte-identical read outcome.  `oracle-static-*` paths do NOT journal — oracle-mode writes are per-validator-local and never part of consensus state. |
| **PB-M-15** | Q-6 resolution 2026-07-30 (consensus-mode periodic snapshots) | Periodic snapshots of the consensus filesystem prevent unbounded WAL replay for late-joining nodes.  Snapshot cadence is a configurable node parameter (config key `storage.consensus-fs-snapshot-cadence`; **no default — operator must set** per 2026-08-03 decision; missing value fails boot with a clear diagnostic).  Snapshot contents are content-addressed (deterministic hash) so that all validators emit identical snapshot roots at the same block height.  Joining node fetches the snapshot at the last-checkpointed block, then replays WAL entries from that block forward.  Snapshot storage: separate on-disk area (config key `storage.consensus-fs-snapshot-dir`) with retention policy governed by the same cadence config. |

## 4. Design questions

The powerbox slice must answer:

- ~~**Q-1 — Blessed-deploy discrimination.**~~ **Resolved 2026-07-30.**  Not per-deploy — per **execution phase**.  Genesis and user execution enter through distinct runtime entry points (`Runtime::play_deploys_for_genesis` at `casper/src/rust/rholang/runtime.rs:329` vs the state-execution paths at 281/352).  The fs-native URN bindings are scoped to the `NormalizerEnv` constructed by the genesis path; the state path omits them.  See PB-B-1 resolved-approach.
- ~~**Q-2 — Per-principal Fs delegation mechanism.**~~ **Resolved 2026-07-30.**  Original question presumed each principal needed a distinct Fs cap.  With uniform-per-bucket bundles and slice-27's cache removal, a shared Fs cap is safe — every `openFile`/`openDir` mints a fresh, independent agent, and authority within a bucket is identical across principals.  Reopens only if a future requirement gives different principals different logical-name→path mappings within the same bucket.
- **Q-3 — Config wiring.** Where does the per-principal bundle come from?
  - Phase 7 produces `Vec<(logicalName, canonPath, kind, mode)>`. Powerbox reads this at boot, maps per-principal.
  - How does the powerbox know WHICH principal each `getFS` lookup is for? Presumably via `rho:deploy:data:deployerId`.
- ~~**Q-4 — Stdio fd resolution.**~~ **Obsolete 2026-07-30.**  Premise (per-principal Fs) is dropped by the PB-M-1 resolution.  There is one shared `Fs` cap; it holds the node process's own (0, 1, 2) at genesis.  The only remaining question — "should operators be able to override the node's stdio destinations via CLI/config?" — is a routine node-config knob (`--stdio-stdin/stdout/stderr` if desired), not a powerbox design decision.  Default: (0, 1, 2).
- ~~**Q-5 — Anonymous deploys.**~~ **Obsolete 2026-07-30.**  Premise (distinct-Fs-per-deployer) is dropped by the PB-M-1 resolution.  With a shared `Fs` cap, every deploy that reaches the runtime gets the same `Fs`.  Authentication policy (should this deploy execute at all?) lives at a different layer — not in Fs handout.
- ~~**Q-6 — Fs lifetime.**~~ **Resolved 2026-07-30 (post-tokenized-cost-accounting).**  Processes maintain filesystem access as long as their agents are in scope; deploys are no longer run-to-completion, so File/Dir agents outlive their originating deploy and reside in tuplespace like any other Rholang term.  It is valid for an agent instance to reference a closed file — closing is a *terminal state transition*, not a deletion of the agent.  Consequences by mode:
  - **Oracle mode:** on node restart, File agent instances come back in a `"closed"` state (the fd table is per-`RhoRuntimeImpl` and gone).  Handled by a startup re-close pass (PB-M-13) that walks the tuplespace, finds every File agent whose state is `"open"`, and rewrites it to `"closed"`.  Subsequent method calls return `FSERR_CLOSED`, matching the semantics an operator would see if `close` had run.
  - **Consensus mode:** the filesystem contents *and* the File agent state must both be part of consensus state.  A joining or rejoining node syncs two layers in order: (1) filesystem contents (PB-M-14 WAL + PB-M-15 snapshots), (2) File-agent state (already replicated via tuplespace, but only meaningful once layer 1 is in place).
  - No per-node long-lived-cap table is needed — tuplespace persistence is the answer.  The Fs cap itself is addressable across deploys via any stored channel; that is not a lifetime concern, it is a scope concern (whoever kept a reference kept access).
- ~~**Q-7 — Mode assignment.**~~ **Resolved 2026-07-30.**  Mode is per-**file/dir**, not per-principal.  The config bucket a path lives in (`oracle-static-*` vs `consensus-static-*`) is the authoritative source: paths declared in `consensus-static-*` are consensus-mode paths, paths in `oracle-static-*` are oracle-mode.  A single principal can hold both kinds of caps simultaneously (opening one from each bucket).  The runtime dispatch decides consensus vs oracle behavior based on the *File cap's origin path* at the moment of a native call — not the calling deploy's identity.  **New invariant (PB-M-16):** paths in the two buckets must be mutually exclusive — the same absolute host path cannot appear (directly or via prefix overlap) in both buckets, because a single filesystem entity cannot simultaneously be consensus-replicated and oracle-local.  Boot validation must reject overlaps.
- **Q-8 — Config-schema evolution.** Phase 7's config layout (spec §1258-1288) uses static `{path, mode}` maps. If powerbox supports policies richer than "static-per-principal" (time windows, capability revocation lists, quota overrides), does the config schema grow? Or stay minimal and let the powerbox source policy separately?

## 5. Fix option catalog for PB-B-1 (URN filter)  —  **Resolved 2026-07-30**

**Chosen approach: phase-scoped URN visibility (variant of Option B).**

Genesis and user execution enter through distinct code paths:

- `Runtime::play_deploys_for_genesis` (`casper/src/rust/rholang/runtime.rs:329`) — one-shot at genesis start, runs only the 14 blessed deploys.
- `Runtime::play_deploys_for_state` / `play_deploy_with_cost_accounting` (`casper/src/rust/rholang/runtime.rs:281, 352`) — runs user deploys under normal block production.

The fs-native URN bindings are placed in the `NormalizerEnv` constructed by the genesis path only.  The state path's `NormalizerEnv` omits them.  A user deploy that tries `new fsOpen(`rho:io:fs:native:*`) in { ... }` finds no binding at normalization and fails with the standard "unresolved URN" error.  No per-deploy signer check, no runtime filter at URN-lookup time — the phase-based entry-point split is the discriminator.

**Rejected alternatives:**

- ~~**Option A — Two URN maps.**~~ Rejected: requires plumbing signer identity to every URN resolution, when the phase separation already gives us the split for free.
- ~~**Option C — Signer whitelist at URN lookup time.**~~ Rejected: same objection as A, plus adds conditional logic to every `HashMap::get` on the URN map.

Both were rejected because they introduced per-lookup discrimination for a distinction that's already made at the entry-point level.

**Sub-consideration:** Phase 8 adds two new `rho:io:fs:native:1.0.0/{lockRange,releaseLock}` URNs.  These join the same set — bound in the genesis-path Env, omitted from the state-path Env.  The registration site is a prefix-based match on `rho:io:fs:native:`, so new URNs under that prefix are covered automatically.
